三个按钮，四步，一个把版本号写回去的坑

工单页那三个按钮，上一版只有 PCD 有配方。现在三个都有，而且配方比上一版多了一步：先写 Product 字段。

四步，顺序固定：字段 → labels → 负责人 → 流转。

为什么字段在第一#

它回答的是"这张票属于哪条线"，与人无关，也不依赖票当前的状态。把它放最前，后面的三步都有一个已经确定的前提——尤其是流转：Under Investigation 在哪些项目上可用，按项目的工作流算，先把票归到对的 Product 上，流转的可用列表才可能是对的那一份。

labels 放第二，负责人第三：label 也是"这条线"的描述，负责人是"谁在接"，流转是"这张票现在处于什么阶段"。这个顺序是在描述一张票该长什么样，而不是在排接口调用的方便。

字段是名字，不是 id#

Product (CG) 在 Jira 里是自定义字段，id 是 customfield_10330——但那是这台实例上的号码，换一台就是另一个数字。所以配方里写名字，每次运行时对着站点的字段目录解析：

const RECIPE_FIELD_NAME = 'Product (CG)';

解析不到就报错，报错里带着这个名字。比起写死 id，这一行的代价是多一次字段目录请求（已缓存），换来的是换实例不用改代码。

顺带，值按字段类型塑形：是个 select 就发 {value: '(CBG)PCD'}，是文本就发原串。这段逻辑上一版给"分类"页写过（payloadFor），这里直接复用——同一个概念不该有第二套写法。

坑：我把版本号写回去了#

功能做完，跑门禁，全绿，然后发版。这一步出事了。

release 流水线拒绝了 tag：

Package, refusing a tag that does not match the version

因为 main 上的 package.json 写的是 1.14.24，而我要发的 tag 是 1.14.26。

原因是这样：前面两个版本（1.14.24 / 1.14.25）都是走 API 合并的——那几天这台机器连不上 github.com:443。API 合并不更新本地仓库，所以本地 package.json 一直停在 1.14.24。而这次发版我写的是：

text.replace('"version": "1.14.25"', '"version": "1.14.26"')

本地文件里根本没有 1.14.25 这个字符串，替换什么都没做——于是我把 1.14.24 的内容提交上去当"1.14.26"，PR 的 diff 甚至是一次降级。

三道防线里，最后一道救了这次：

  1. PR 的 CI 没拦住——版本号降级不影响任何测试，它只影响发布。
  2. 合并前的门禁 没拦住——ship 里那句"两个文件都是 1.14.x"对 1.14.24 是成立的。
  3. release.yml 拦住了：tag 名与 manifest 不一致就拒绝打包。

所以修法不是"下次小心"，而是它本来就该拦：版本号是唯一一个必须由产物自己证明的东西。tag 是人打上去的，manifest 是代码里的；两者不一致时，能证明哪个是真的只有前者。流水线选择了怀疑人。

修的时候做对了两件事：

  • 删掉错的 tag 再重打，而不是在同名 tag 上"改指"。改指会让已经拉过它的人拿到两个不同的 1.14.26。
  • 从远端内容改版本号，不从本地文件改。本地文件在这件事上已经被证明不可信了。

结果#

  • 659 组断言（+1：三个模块各自的字段值、label 集合、负责人、流转；含"label 已在票上就不重复写"）
  • 297 个变异全部命中（+3：跳过配方、跳过字段步、跳过失败即停）
  • check / build / verify（真 Chrome，十页）全绿

版本 v1.14.26。
