「只要 key 和 value」为什么还是失败：一个下拉框的锅

有人拿着截图来问：我只要导入两列，key 和 value，为什么一直用不了 value？已经改了很多版了。

截图里写着：

13 issue(s) ready to import
Not used: Value

CSV 是对的。问题在那个他根本没看的下拉框——「What is in the file」还停在 Historical issues。

为什么这不算「用户的错」#

当类型选成「历史 issue」时，那份两列文件照样解析成功：

  • 第一列叫 Key，正好命中 issue 的 key 字段；
  • 于是每一行都变成一张「没有 summary、没有状态、没有日期的 issue」；
  • 第二列 Value 找不到对应的 issue 字段，被列进 Not used。

界面上每一个字都是真的。13 行确实就绪，Value 确实没被使用。 但没有一个字提到「你选错了导入类型」，所以唯一合理的下一步就是——回去改 CSV。他改了很多版。

修法：类型是提示，不是命令#

新增一个判据 looksLikeLookupExport()，用「缺席」来判断：

真实的 Jira 导出，必带 summary / status / type / priority / created / project / reporter 里的至少一个。 一个都不带、且不超过三列的文件，根本没有 issue 的形状——不管它第一列叫什么。

命中就把文件按 lookup 表重读一遍，并且做到三件事：

  1. 选择器跟着改——控件说 lookup，结果才是 lookup。一个显示「历史 issue」却给出 lookup 结果的界面，是同一个谎，只是更小声。
  2. 预览里说清楚：「这份文件只有一个 key 和一个 value，没有 issue 字段，已按 lookup 表读取。」
  3. 留一个逃生口：Preview as historical issues 按钮。真有那种只有一列 key 的「薄」issue 清单，按一下就走回原路，选择器也退回 issues。

最后这条很关键。判据是启发式的，启发式必须能被推翻——否则我就是用一个新的「自动行为」替换了一个旧的「手动困惑」。

三处判据的边界#

写成代码只有六行，但边界值得列出来，因为每一条都对应一种真实文件：

文件判据结果
Key,Value + 13 行无 issue 字段，2 列转为 lookup ✓
Issue key,Summary,Status,Created有 summary/status/created保持 issues ✓
只有一列 Key命中判据，但 lookup 读不出条目保持 issues ✓（转换以「真的能读」为前提）
a,b,c,d,e 五列超过三列保持 issues ✓（这种要的是列映射，不是换导入器）

第三条是我最在意的：判据只负责「怀疑」，转换由「重读成功」拍板。否则一个只有 key 的单列清单会被换成一个空表，比原来更糟。

验证方式也换了个位#

浏览器门禁里那一步（7c），以前是先手动把类型切到 lookup 再粘贴。现在改成：保持默认的 Historical issues，直接粘贴两列。

因为那才是他当时的操作。断言三件事：

  • 预览变成长度正确的 lookup 结果（3 mapping(s) under "team"）；
  • 选择器的值已经是 lookup；
  • 那句「已按 lookup 表读取」在屏幕上，且逃生按钮在。

只测「切对之后能不能导入」，测不到这个 bug——它要测的是「切错之后会怎样」。

一个更一般的教训#

我这一轮之前还改过两版：一次是让属性名兼容任意拼写，一次是修尾逗号造成的幽灵列。两次都在数据侧找原因，两次都不是根因。

不是因为我蠢，是因为界面给的信号把我指向了那里。当错误信息描述了症状而不是原因时，人会去修症状。 所以真正要修的不是那行提示的措辞，而是「让系统自己纠正它显然能判断的事」。

一个下拉框的默认值，值三版工时。

顺带一句：这一版之后，导入哪怕选错类型也不会进垃圾数据了。但如果你确实要导 issue，请确认文件里至少有 Summary 或 Created 之一——那才是它和 lookup 表的分界线。
