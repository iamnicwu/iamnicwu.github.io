导入了 lookup 表，Rebalance 却说「没导入」

一个真实的报障：「我导进去我的同事以及负责的模块，但一直 load 不到。」

表格没错。错的是我在代码里写死了一个词。

三种失败，一句话#

Rebalance 需要一张 lookup 表来知道「谁和谁能互换工作」，读表的代码是这样的：

entries.filter((e) => e.attribute === 'team')   // ← 就这一行

而设置页导入的表，属性名来自文件内容或数据集名：三列表 (attribute,key,value) 用第一列的值；两列表拿你填的数据集名当属性。于是：

你导入了什么属性实际是老代码的结果
team,alice,Paymentsteam能用
module,alice,Paymentsmodule一行都匹配不上
两列 alice,Payments，数据集名「同事」同事一行都匹配不上
导成了 issues（而不是 lookup）—一行都没有

这四种情况，页面说的是同一句：「No lookup table imported yet.」 于是人会去重导一次那个明明已经导进去的文件——这就是一个把人往错误方向推的提示。

修法：属性名从「要求」降级成「偏好」#

rebalance.json 里的 departmentAttribute 现在只是首选：导入里真有 team 就用它；没有就用导入自己的那个，并且把替换说出来。

页面上现在长这样：

2 group(s), 4 people, 4 row(s) · grouped by “module” · (rebalance.json asks for “team” — this import does not carry it)

顺序是刻意的：先给数字（2 组 / 4 人 / 4 行），再给依据（按哪个属性分的），最后才是那句"我改了默认"。没有数字的提示，读的人无法判断该不该信。

剩下的失败也各说各的：一个数据集都没导入 → 告诉你去哪里导；导入了但不是 lookup → 列出「你导的是什么」；有 lookup 但没有可用的 人/组 对 → 直说。

顺带加的两个体检#

分组这件事有两种写反/写歪的方式，在 picker 里都看着很正常：

  • 每个组只有 1 个人：这是表写反了的特征——key 是模块、value 是同事。它会被当成"一个只有一个人的部门"，而这样的部门无法平衡。
  • 同一个人出现在多个组：平衡时只按你选的那个组算一次，别的组里的他会被静默忽略。

两者都只是警告，不阻止执行——但至少在按下"应用"之前，你能看见。

一个判断留在这里#

Rebalance 分组的意思是「这些人可以互相接手对方的票」，不是组织的正式部门。所以一个模块的三个 owner 是一个完全合法的分组，部门只是同一件事的另一个名字。这条想清楚之后，「属性必须叫 team」就自然站不住了——它约束的是命名，不是语义。

怎么验证的#

npm run verify 里加了一步真实场景：往 storage 写一张属性为 module 的 lookup，打开页面，断言 picker 里出现两个组、注释里写出「grouped by “module”」并且带上「rebalance.json asks for “team”」这句。单元测试还钉住了两个纯函数：属性解析的优先级、反向表和多组归属的告警。

教训很短：一个提示如果把几种不同的原因说成同一句话，它就不是提示，是噪音。
