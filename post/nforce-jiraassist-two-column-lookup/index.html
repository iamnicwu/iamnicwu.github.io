一张 lookup 表只需要两列：key 和 value

2026年11月10日 · 1 分钟 · Nick Wu

有人跟我说：lookup 表我只要 key 和 value，然后把数据读出来。

听起来是个简单要求，但它把之前几轮埋的两个毛病同时戳破了：一个是我让它太像「配置」，另一个是我只告诉它「成了」却没让它「看见」。

一、为什么当初不是两列#

最早设计 lookup 表时，我加了第三列 attribute：

attribute,key,value
team,82012717,(CBG)PCD
sla_days,High,2

理由是：同一张表既能放「谁在哪个组」，也能放「High 的 SLA 是 2 天」，两边共用一个导入器。这在设计上不算错，但它给最常见的用法——一张同事名单——加了两道手续：

  1. 得写第三列，每行都重复一遍 team；
  2. 两列文件也行，但必须在页面上填一个「Data set name」，那一栏会成为属性名。

第二道手续是我自己埋的雷。因为名称栏留空时，页面会拿文件名兜底。于是同一张表，存成 team_setup.csv 导入是属性 team_setup，改个名字再导入就变成 my-team。而均衡页问的是 team——问不到，就说「没有导入 lookup 表」。

一个「必填但其实不该必填」的字段，会造出「文件明明导了，系统说没导」这种最难查的错误。

二、现在：两列就是全部#

key,value
82012717,(CBG)PCD
82012718,(CBG)LTS
  • 不用写第三列，也不用填名字。
  • 属性没有消失（均衡页仍按它筛行），只是不用手写：没名字就落到 team。
  • 真给了名字，就用你给的——这保证了把分组叫 module 的团队不用改文件。
  • 一个文件要装多组映射（比如再加一张 sla_days 表），那才用回三列。

判据只有一条：这张表描述的是「谁和谁能互换工作」，那就两列。

三、「把数据读出来」比想象中重要#

真正让我改主意的不是格式，是这句话的后半句。

过去页面告诉你的是 13 row(s)。这个数字是无法验证的——它既可能是对的 13 行，也可能是「表头被当成数据」或者「尾逗号多出一个空列」之后剩下的 13 行。你唯一能做的，是相信它。

现在两端都能看见：

设置页，每个 lookup 数据集多了一个 View rows，按导入顺序列出存下来的 key, value（前 50 行 + 余数）。它读的是存储里的真实内容，不是预览缓存。

均衡页，选一个组之后，直接把这个组读到的 key 列出来，旁边写着按哪个属性分的组：

In this group   11 key(s) read from the table, grouped by "team"
82012717  82017576  82012791  …

这两处看起来像「又加了一个方便功能」，其实是把不可验证的东西变成可验证的。之前那几个真实故障——尾逗号造出的幽灵列、表左右写反、表头被吞进数据——在数字上都一样，在名单上都一眼能看出来。

顺便把预览也改了：它现在展示的是将要存下的形状（attribute, key, value），而不是文件的原始表头。合成出来的属性不该在导入之后才第一次出现。

四、这次改出来的 bug，被自己的门禁抓了#

改这块的时候我删掉了均衡页的一句副标题，连带删掉了里面那个 <code id="dept-attribute">team</code> 元素——但渲染函数还在往它写：

$('dept-attribute').textContent = snapshot.departmentAttribute || 'team';

null.textContent 抛错，被页面自己的 catch 吞掉，于是 loadState() 半路终止，下拉框停在 HTML 里的默认文案上。

结果是：数据在存储里，页面显示「No lookup table imported yet」。 和我上一轮刚修的那个 bug 长得一模一样，只是原因相反——上次是筛选条件错，这次是渲染时炸了。

抓到它的是浏览器门禁里的第 7b 步：它读 #page-warnings 的文本，于是那句 Cannot set properties of null (setting 'textContent') 直接出现在失败信息里，指名道姓。

这件事给我的提醒比代码本身重要：try/catch 加一句「出错了」的渲染，会把「程序崩了」伪装成「数据是空的」。 空状态和错误状态必须在视觉上分开，否则用户永远在修数据，而问题在代码。

五、新增的那一步验证#

npm run verify 里加了 7c：驱动真实的设置页——粘贴两列、名字留空、点预览、点导入、点 View rows，断言三行都读得出来。

为什么不直接往 storage 写一份 fixture？因为「名字留空」这个决定散在三处：输入框的取值、预览的文案、导入的调用。写 storage 能证明第四处（读）对，前三处一个都没测到。而这次改动里最值钱的恰恰是前三处。

顺带说个实现细节，踩了两回：Runtime.evaluate 的表达式本身是塞在模板字符串里的，\n 会被模板字符串先吃掉一层，浏览器那边就收到一个裸换行，报 Invalid or unexpected token。改成 String.raw 之后，反斜杠才真的传到浏览器手里。

结果#

  • 导入：两列 CSV，不填名字，行落到 team；填了名字就用名字；三列仍支持多组。
  • 读回：设置页 View rows、均衡页的组成员名单，都是存储里的真数据。
  • 修掉：一个把「渲染崩溃」伪装成「没有数据」的空引用。
  • 验证：603 组单测、265 个变异全部被预期断言抓住、npm run verify 新增 7c 并全绿。

一个字段的「必填」和一个状态的「可见」，看着都是小事。但它们决定了出错时你是在改数据还是在改判断——而后者通常要快得多。
