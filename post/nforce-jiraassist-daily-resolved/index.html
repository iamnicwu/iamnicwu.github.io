一张按工号的名单：谁能接手，以及这周谁真的干了活

2026年11月9日 · 1 分钟 · Nick Wu
目录

  • 二、新页面：每天谁 resolved 了多少
  • 三、顺手修掉一个"绿灯但没测"的结构问题

同一张 lookup 表，两个问题：谁能接手我的票（Rebalance），和这周谁真的把票做完了（新页面 Daily resolved）。

一、key 就用工号#

名单是这样写的：

attribute,key,value
team,10001234,(GROUP)Alpha
team,earl,(GROUP)Alpha

key 是工号，而 Jira 那边 assignee = 10001234 是有效 JQL。这就说明工号本身就是标识符。

旧代码不理解这一点：它把每个 key 都拿去"解析成 Jira 用户"（username / accountId / 邮箱 / 显示名），再拿解析结果去分配。代价有两个：

  • 一个人一次用户搜索——13 人的名单就是 13 次往返，纯浪费；
  • 站点的用户搜索往往不索引工号，于是每个人都会收到一句 “not a user this site recognised”，而这份名单明明是对的。

现在默认照抄：key 是什么就发什么。要解析的场合（Jira Cloud 需要 accountId，CSV 里不可能写得出来）在 rebalance.json 里写 "resolveMembers": true 打开旧行为。

判断的标准只有一条：这个字符串能不能被站点自己的 JQL 接受。能，它就是标识符；不能，才需要解析。

二、新页面：每天谁 resolved 了多少#

选一个组、选一个窗口（7 / 14 / 30 天，含今天），得到一张 人 × 天 的表，加一个每天总量的柱状图。

三个决定值得写下来：

日期取 resolutiondate 的前十个字符，也就是 Jira 页面自己显示的那一天。用 Date 再按时区推一遍，会让晚上 23:50 完成的票跑到第二天去——而旁边的 issue 页面还写着昨天，报表就和它自己打架。

一次查询，不是一人一次：assignee in (…) AND resolutiondate >= "YYYY-MM-DD"。名单决定 in 列表，所以这周一张票都没关的同事也会有一行零。“Ana 这周什么都没做"通常正是结论，只列忙人的表把结论藏掉了。

丢掉的必须被数出来。三种情况会掉出这张表：票的 assignee 不在这个组里、日期落在窗口外、根本没有 resolution date。它们各自计数并打印在表格下面——一个总数悄悄小于查询自己返回的条数，是最没人发现的那种错。

图表只画每天的总量一条：按人堆叠就是 180 像素上放十一块颜色，图例没人读；而"这周中间有没有空档"这个问题，一个总量就答完了。人跟人的比较在表里，而且表按总数排好序。

三、顺手修掉一个"绿灯但没测"的结构问题#

npm test 末尾有一条「README 必须引用本次断言数」的守卫，它靠"所有断言都过了"才执行。我在最近几轮不断往文件末尾追加测试段——结果新段全落在守卫之后，守卫量到的是半截计数，于是连续几轮都在自我跳过：green，但没人守着。

现在文件里有一条明确的线：

/* ──────── End of tests ──────── */
// New sections go ABOVE this line. …

守卫下面加了这句之后，它第一次跑就抓到了 README 里过期的数字（580 vs 实际 602）。

一句总结：如果一个检查只在"一切都好"时才运行，那它必须真的在最后运行。
