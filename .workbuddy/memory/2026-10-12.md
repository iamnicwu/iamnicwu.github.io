## 配置要点（改 hugo.toml 前先读）

- `[outputs] home = ["HTML","RSS","JSON"]` —— PaperMod 的 Fuse.js 搜索依赖这个 `index.json`

## 踩过的坑（都是真 bug，不是风格问题）

1. **`{{< relref >}}` 不能写在 Markdown 链接的 `()` 里** —— 会产出 `href=//tags/`，浏览器按协议相对 URL 解析成 `https://tags/`，必然 404。放进原生 HTML 的 `href="..."` 里则正常。
2. **`render-link.html` 里不能对以 `/` 开头的路径用 `relURL`** —— 会拼成 `//tags/`。只对真正相对的路径才过 `relURL`。
3. **`cover.image` 会被 `absURL`** —— 本地用生产产物预览时，封面图指向线上域名而拿不到。要本地看封面得单独构建：
   `hugo --baseURL http://127.0.0.1:4002/ -d /tmp/preview`
4. **少四个 favicon 文件 → 每页 4 个 404**。PaperMod 的 `head.html` 默认引用 `favicon-16x16.png` / `favicon-32x32.png` / `apple-touch-icon.png` / `safari-pinned-tab.svg`，`static/` 里只有 `favicon.ico`。已从 ico（内部是 352×352 PNG）派生补齐。
5. **`.project-version` 徽章被挤成两行** → `flex: 0 0 auto; white-space: nowrap`。
6. **窄图被放大发虚**：侧栏截图只有 400px 宽，正文栏 720px，顺其放大 1.8 倍在 Retina 上明显糊。加了 `.post-figure.is-narrow`（限宽 440px 居中），这类图要用原生 HTML 写。
7. **选封面优先挑 1440 宽的整屏截图**：列表缩略图会被裁成横幅，`400x1416` 这种超长竖图裁完基本看不出内容；只有方形图标时用 Chrome 渲染合成一张 1200×675 横幅再当封面。

## 校验手段（可复用）

- 全站内部链接校验要**同时覆盖 `/…` 和 `https://iamnicwu.github.io/…` 两种写法**，并 `decodeURIComponent`（中文标签页是 percent-encoded），否则漏检。当前 488 条全绿。
- Chrome + CDP 截图核对：必须加 `--no-proxy-server` 且清掉 `HTTP_PROXY`，**每次用全新 `--user-data-dir`**（复用 profile 会缓存上一轮的 404，看起来像图片全坏）。
- `resources/_gen` 缓存会让样式改动不生效；构建异常先 `rm -rf resources/_gen`。
- 本机 Node 命令一律要 `env -u NODE_OPTIONS`。

### 关键坑：本机到 github.com 不通，但 api.github.com 通

| 主机 | 结果 |
| --- | --- |
| `github.com` | ✗ 经代理 502 CONNECT、直连 443 超时 |
| `api.github.com` | ✓ 200（直连即可） |
| `codeload.github.com` / `raw.githubusercontent.com` / `objects.githubusercontent.com` | ✓ 可达 |
| 其他站点（如 registry.npmjs.org） | ✓ 200 |

所以 `deploy.sh`（内部 `git clone` + `git push`，都走 github.com）在当前网络下**必然失败**，
而 `git ls-remote` 也一样。**绕法：GitHub Git Data API**（`POST /git/blobs` → `/git/trees` → `/git/commits` → `PATCH /git/refs/heads/<branch>`）。
已把这条通道沉淀成仓库里的 `scripts/deploy-via-api.mjs`，README 也写了何时用它。

用 API 建树还有两个额外好处：
1. **不加 `base_tree` 时，新树就是完整快照** —— 不含的路径自然消失，不需要 `rsync --delete`（也就不会误删）。
2. 提交前可以 `GET /git/trees/<sha>?recursive=1` 回读校验文件数与本地是否一致，不一致就中止，宁可不动分支。

### 这一段的两个脚本 bug（都栽在 API 参数上）

1. **`POST /git/trees` 的键名是 `tree`，不是 `entries`** —— 传错只会得到
   `422 Invalid tree info`，报错信息完全不提示是哪个字段，很容易往"路径有问题"的方向查。
   定位手法：写最小用例逐个排除（扁平路径 / 嵌套路径 / 空文件 / 点文件 / 中文路径 / 不带 type），
   发现**单个用例全部 201 通过**，才反推问题不在数据而在请求体形状。
2. **校验树时要把目录条目排除** —— `?recursive=1` 返回里含 `type: "tree"` 的目录条目，
   直接和 `git ls-files` 比对会报出一堆"多余项"（`.workbuddy`、`content/posts` 等）。
   只比 `type !== "tree"` 的条目。

# 追加：把站点迁到自定义域 nickwu.fun

## 背景与前置事实

- `nickwu.fun` 此前**正跑着 LobeChat**（Vercel）：apex A `76.76.21.21`、`www` CNAME `cname.vercel-dns.com`、apex 301 到 www。
  DNS 托管在**阿里云**（NS `dns25/dns26.hichina.com`）。
- 仓库历史里这个域名**被用过**（还有更早的 `nickwu.me`），最近一次是被 `Delete CNAME` 移除的。
- 用户选择 **apex 主域**（LobeChat 自行迁移），所以博客占用 `nickwu.fun` 本身，不是 `www`。

## 顺序必须这样（chicken-and-egg）

**先改 DNS，再设 GitHub 自定义域。** 反过来会把站点打断：设了自定义域后 `iamnicwu.github.io` 立刻 301 到新域名，
而新域名 DNS 还没生效 → **整站不可访问**（用户和我都进不去，只能干等）。本次是先让用户改完 DNS，验证通过后才动 Pages 设置。

## apex 指向 GitHub Pages 的完整记录集

| 类型 | 值 |
| --- | --- |
| A ×4 | `185.199.108.153` / `185.199.109.153` / `185.199.110.153` / `185.199.111.153` |
| AAAA ×4 | `2606:50c0:8000::153` ～ `2606:50c0:8003::153` |
| CNAME（www） | `iamnicwu.github.io.` —— **不带仓库名**，带仓库名是另一套（`<user>.github.io` 的 repo 写法） |

- **多余的 A 记录会导致 Let's Encrypt 签发失败**（DNS-01 校验可能打到别人的服务器）。
  本次查过：无多余 A、**无 CAA 记录**（有 CAA 且没放行 `letsencrypt.org` 同样会失败）。
- 本机验证 DNS 的三板斧：`dig @<权威NS>` 直查（绕公共缓存）、`@223.5.5.5/@119.29.29.29/@8.8.8.8` 看缓存刷新、`+short`。
  `1.1.1.1` 本机不可达（不是问题）。

## `build_type = legacy` 的两个连带后果

1. 发布源是 `master` 分支**根目录**（不是 `gh-pages`），所以**必须是根目录里躺着一个 `CNAME` 文件**。
   → 本地 `static/CNAME` 内容 `nickwu.fun`，Hugo 会把它拷进 `public/CNAME`。
   本项目用 API 整树覆盖 master，**一旦漏掉 CNAME，等于顺手取消了自定义域**。
2. 不能靠 `hugo --baseURL` 之类的构建期注入域名，域名是仓库里的一个文件。

## 设置自定义域不用点界面

`PUT /repos/{owner}/{repo}/pages`，body `{"cname":"nickwu.fun"}` → **204**。
随后 `GET .../pages` 看到 `protected_domain_state: "verified"` —— 说明**域名所有权校验状态仍在**（历史验证过），
**不需要再加 TXT 记录**。若该字段是 `unverified` 才需要走 TXT 校验。

**踩坑：`https_certificate` 字段在证书签发前根本不出现在响应里。**
它的缺席就是"还没签发"，不要误读成 API 不支持。

## curl 观察证书的三个维度

```bash
curl -s --noproxy '*' -o /dev/null -w 'HTTP=%{http_code} SSL=%{ssl_verify_result} IP=%{remote_ip}\n' https://nickwu.fun/
echo | openssl s_client -connect nickwu.fun:443 -servername nickwu.fun 2>&1 | openssl x509 -noout -subject -issuer -dates
```

- 证书没签发时，`openssl` 拿到的是 GitHub 的兜底通配证书 `subject=CN=*.github.io` —— **这就是"证书还没轮到你这个域名"的判据**，
  比 `ssl_verify_result=1` 更有信息量（后者只说明"校验没过"）。
- `%{remote_ip}` 能看到实际打到了哪个边缘节点（`185.199.11x.153`），可用于确认 DNS 已生效。

## 域名没生效也能先做的验收（重要）

HTTPS 证书要等几十分钟，但 **HTTP 早就通了**，所以别干等：

1. `http://nickwu.fun/` 已经 200 → 说明 DNS + Pages 自定义域 + CNAME 文件三者都对。
2. `iamnicwu.github.io` → **301** → `nickwu.fun`；`www.nickwu.fun` → **301** → `nickwu.fun`。
   （证书生效并开启 Enforce HTTPS 后，这两个 301 的目标会从 `http://` 变 `https://`。）
3. 页面内的 `canonical` / `og:url` / RSS / JSON 链接全是 `https://nickwu.fun/`，旧域名残留 **0 处**。

## 验证脚本的这个 bug 值得记一笔

BFS 爬虫用 `new URL(u, ORIGIN).origin !== ORIGIN` 判是否站内 —— **当 ORIGIN 是 `http://` 而页面里写的是 `https://` 绝对链接时，
整片页面会被误判成站外而漏爬**。本次表现为"只爬到 8 个页面，`/archives/`、`/search/`、所有标签页全丢"，
看起来像站点缺页，实际是脚本假阴性。**改成比对 `hostname` 而不是 `origin`**，重跑得到 64 个 URL / 19 页面，全 200。

# HTTPS 证书不签发的根因：`caa_error: Dnsruby::ResolvTimeout`

## 决定性证据来自一个不起眼但极其好用的端点

```
GET /repos/{owner}/{repo}/pages/health
```

- **第一次请求返回 `202` + 空 body `{}`** —— 意思是"健康检查进行中"，**不是**接口不存在。
  轮询几秒后变成 `200`，才拿到完整 JSON。**不知道这一点会以为接口坏了而放弃**。
- 拿到的关键字段：

| 字段 | apex `nickwu.fun` | www `nickwu.fun` |
| --- | --- | --- |
| `is_a_record` | true | false（是 CNAME） |
| `has_cname_record` | false | true |
| `is_cname_to_github_user_domain` | false | **true** ✅ |
| `is_pointed_to_github_pages_ip` | **true** ✅ | false |
| `dns_resolves` | **true** ✅ | true ✅ |
| `is_valid` | **true**（配置本身没错） | true |
| `responses_to_https` | false | false |
| `https_error` | `peer_failed_verification` | `peer_failed_verification` |
| **`caa_error`** | **`Dnsruby::ResolvTimeout`** ❌ | **`null`** ✅ |
| **`is_https_eligible`** | **`false`** ❌ | **`true`** ✅ |

**结论：GitHub 用自家的 DNSSEC 校验解析器（Ruby 的 Dnsruby）去查 apex 的 CAA 记录，超时了。**
`is_https_eligible: false` 是证书签发的闸门 → 证书永远不会自动签发。

## 为什么是 apex 出问题、www 没事（关键机制）

RFC 8659 规定：CAA 查询遇到 **CNAME 要跟着走到目标域**。所以
- `www.nickwu.fun` 是 CNAME → `iamnicwu.github.io` → CAA 实际查的是 `github.io`（GitHub 自家 DNS）→ 通 ✅
- `nickwu.fun` 是 apex、A 记录 → CAA 必须查阿里云 NS（`dns25/dns26.hichina.com`），无记录还要向上递归到 `.fun` 顶级域 → **超时** ❌

## 已排除的所有"我方能修"的原因

| 假设 | 实测结果 |
| --- | --- |
| DNS 没生效 | 权威 + 公共 DNS 都是 4 条 A + 4 条 AAAA ✅ |
| 多余 A 记录（Vercel 残留） | 无 ✅ |
| CAA 记录挡着 letsencrypt.org | **根本没有 CAA 记录**（`nickwu.fun` 和 `.fun` 都查过，`8.8.8.8`/`223.5.5.5` 复核）✅ |
| 权威 NS 不响应 CAA | 查询矩阵全绿：默认 / TCP / 无 EDNS / EDNS=0 / +DO / +norecurse / ANY / 未定义类型 / dns26 / Cloudflare / Quad9 —— **全部 NOERROR** ✅ |
| 权威 NS 慢 | `dig +trace` 末级 `dns25.hichina.com` 应答 **54ms** ✅ |
| DNSSEC 校验链断 | `nickwu.fun` 未签名；`.fun` 有 DS/NSEC3，迭代解析能拿到"无 DS"的证明 ✅ |
| Let's Encrypt 限流 | crt.sh 查最近 7 天 **0 张**，远低于 5 张/周 ✅ |
| GitHub Pages 事故 | githubstatus.com `Pages: operational`、0 起事故 ✅ |
| Pages 构建失败 | 构建记录全 `built`、`err=无`（含手动 `POST /pages/builds` 触发的一次）✅ |

**crt.sh 是最有信息量的一步**：它显示 `nickwu.fun` 最近一次签发是 **2026-08-14**（Vercel/LobeChat 时期），
之后没有任何新签发 —— 直接区分了"LE 还没签"和"签了没生效"。

## 社区结论：这是 GitHub 侧的已知缺陷

GitHub Community **#209977**、**#209142** 报告了**完全相同**的症状（`caa_error: Dnsruby::ServFail` /
`ResolvTimeout`、`is_https_eligible: false`、公共解析器看一切正常）。要点：

- 社区实测：把 **DNS 托管迁走**（如 Cloudflare，**灰云 / DNS-only**）的域名，**1–2 天内都拿到了证书**；
  留在原托管商的那一个，**至今还是 `*.github.io` 兜底证书**。
- GitHub Support 曾回复其中一位作者：**"你的配置是正确的，签发问题在我们这边"**。
- 官方说法：证书最长 24h；但此症状下等待无效。
- **警示：不要反复删/加自定义域** —— **每次重加都会重启证书队列**。本次我只做了一次"重复 PUT 保存"，没做 remove/re-add。

## 当前待用户决策的三条路

1. **加一条显式 CAA 记录**（`nickwu.fun. CAA 0 issue "letsencrypt.org"`）—— 1 分钟、零风险、本来就该加；
   有可能让 CAA 查询「直接命中」而不必走 NODATA + 向上递归那条会超时的路径。
2. **DNS 托管迁到 Cloudflare**（域名注册仍留阿里云，只换 NS，灰云 DNS-only）—— 社区实测最可靠。
3. **改用 `www.nickwu.fun` 作自定义域** —— 无需改 DNS（www 的 `is_https_eligible` 已经是 true），
   但主域会从 apex 变成 www（与用户最初"主域"的选择不符）。

## 一个待验证的假设（下次继续）

**GitHub 只在「设置/重设自定义域」的那一刻评估签发资格，之后不会重试。**

## 关于 IPv6 / AAAA 的一条经验

`dns25.hichina.com` 单台 NS 挂 **8 条 A + 1 条 AAAA**。多后端 + 轮询会让
`dig` 每次命中不同后端 —— 这正是发现"多版本 zone"的手法：**逐台 IP 直查再比对 SOA 序列号**，
比反复查同一主机名有效得多。

# 触发签发尝试（17:11–17:22）+ 绕过方案的调研结论

## 做了什么

趁闸门稳定打开（连续 3 次 `is_https_eligible=true`）时，做了一次标准的 remove + re-add：

1. `PUT /pages {"cname":null}` → 204。回读 `cname=null`、`html_url=https://iamnicwu.github.io/`、
   `protected_domain_state=null`、`https_enforced` 变 **true**（默认域名强制 HTTPS）。**移除真的生效了** —— 
   等构建完成后 `nickwu.fun` 会变 **404**。**legacy 模式下 API 清 cname 是有效的**，不需要动 CNAME 文件。
2. 等 10 分钟。
3. `PUT /pages {"cname":"nickwu.fun"}` → 204，`protected_domain_state` 回到 `verified`，站点恢复 200。
4. 盯了 ~20 分钟，证书仍 `CN=*.github.io`，`https_certificate` 仍为空。

期间哨兵抓到闸门仍在抖：17:22 开 → **17:28 关（ResolvTimeout）** → 17:33 开。
**所以触发那一刻（~17:22）闸门是开的，时机没错。**

## ⚠️ 重要更正：不要用 Cloudflare 橙云代理绕过

一度以为「橙云代理 + Flexible SSL」能彻底绕开 GitHub 的证书问题（访客侧 HTTPS 由 Cloudflare 提供）。
查证后**明确排除** —— GitHub Support 官方原话：

> Cloudflare 默认开启 HTTP/DNS 代理，**导致 GitHub 无法看到生成 HTTPS 证书所需的 DNS 记录**。
> ……**一旦证书签发成功，不要重新开启 Cloudflare 代理，那会导致证书将来无法自动续期。**

即：橙云会让 GitHub 的域名校验失败（DNS 不指向 GitHub 的 IP），既阻碍签发也破坏续期，
还可能让自定义域被判定无效。**要给 GitHub Pages 用 Cloudflare，必须灰云（DNS only）。**

## ⚠️ 重要更正：签发预期时长的量级

GitHub Support（community #191375）原话：

> DNS 就位后，**需要到仓库设置页触发一次 DNS 重查**来启动签发流程。
> 而且「**证书请求大约需要一小时**」。

→ 我 17:22 做的触发，到 17:40 才 18 分钟。**当时就下"没用"的结论为时过早**，要盯到 ~18:30。

## 两条真正能绕过闸门抖动的路

**A. 加显式 CAA 记录（唯一能保住 apex 作主域的方案）**
机制：有 CAA 记录时，`CAA nickwu.fun` 是**正回答**，解析器不必走
「NODATA → 向 `.fun` 顶级域递归 → DNSSEC 校验无 DS 证明」这条会超时的路径。
上次用户加过但**没进 zone**（16 台后端全空）。重加后要用
`dig +short CAA nickwu.fun @dns25.hichina.com` 确认能看到 `0 issue "letsencrypt.org"`。

**B. 改用 `www.nickwu.fun` 作自定义域（结构性绕开，不碰 DNS）**
机制：`www` 是 CNAME，RFC 8659 规定 CAA 查询要**跟着 CNAME 走到目标域**，
于是校验落在 `github.io`（GitHub 自家 DNS）→ **闸门天生不抖**。
实测：全程 `www` 的 `is_https_eligible` **一次都没关过**，apex 则反复跳。
代价：canonical 从 apex 变成 www（GitHub 会把 apex 301 到 www）。用户最初选的是 apex 主域。
补充：GitHub 的自动证书覆盖 apex + www 这一对，所以 www 作主域时 `https://nickwu.fun` 大概率也能用。

**C. 找 GitHub Support** —— 附上 `pages/health` 里的 `caa_error`，让他们强制签发。
社区里对同一症状，Support 回过「配置没问题，问题在我们这边」。

## 收尾：apex 决定留空 + 线上复验

### 定案

用户拍板：**清掉 apex 记录，把 nickwu.fun 整个腾出来**（不迁 Cloudflare、不指回 Vercel）。
所以这个 zone 最终只有一条记录：`blog.nickwu.fun. CNAME iamnicwu.github.io.`。
控制台要删的：`@` 的 4×A + 4×AAAA、`www` 的 CNAME、以及当初加的那条 `CAA @`。

**为什么把 CAA 也删掉**（不是可有可无）：CAA 按域树向上继承，留着
`0 issue "letsencrypt.org"` 会让 `nickwu.fun` 底下**任何**新子域名签证书都被限制成只准 LE。
Vercel / Cloudflare 可能用 Google Trust Services、ZeroSSL —— 届时会看到
「证书签不出来但翻遍日志找不到原因」这种最贵的故障。

### 实测证据：CAA 跟着 CNAME 走（这次终于量到了）

`dig +short CAA blog.nickwu.fun` 返回的是 **`github.io` 自己的那张列表**：

```
0 issue "digicert.com" | 0 issue "letsencrypt.org" | 0 issuewild "sectigo.com"
0 issue "sectigo.com" | 0 issuewild "letsencrypt.org" | 0 issuewild "digicert.com"
```

`letsencrypt.org` 在列 → 不阻塞。这一条把整套推理闭环了：
blog 是 CNAME，CAA 校验跟到 github.io（GitHub 自家 DNS，永不超时）；
apex 没有 CNAME 可跟，只能直查阿里云权威 NS，而那条路会超时 → 闸门抖 → 证书永不签发。

### 线上复验（`node scripts/verify-live.mjs`）

**62 个 URL 全部 200，无站外跳转。** 站点内容层没问题。

### 新踩的坑：爬虫把正文里的 `href=` 当成真链接

第一次爬报 `/home` 404。真身是 nforce-autotest 那篇里的一张表，讲目标选择器四种写法：

```
xpath=//a[@href='/home']
```

宽松的 `(?:href|src)=` 扫全文会匹配到它 → 去请求 `/home` → 404 →
报出一个**根本不存在的站点故障**。

修法走了两步才对：
1. 先剥 `<pre>`/`<code>` —— **不够**。只挡住代码块里那份，挡不住正文里的行内代码。
2. 正解是**收紧正则，只认真标签**：
   `/<a\s[^>]*?href=["']?([^"'\s>]+)|<(?:link|script|img|source)\s[^>]*?(?:href|src)=["']?([^"'\s>]+)/gi`

  代码块里的标签会被 markdown 渲染器转义成 `&lt;a href=`，天然不误匹配。
  同时补上剥 `<script>` / `<style>`。

固化成了 `scripts/verify-live.mjs`（原来只在 `/tmp` 里，会丢）。
注意两个捕获组，取值要 `m[1] || m[2]`。

教训写成一句：**「爬自己的站」不能扫全文找 `href=`，得认标签** ——
文章里有语法示例是常态，而这类假阳性会让人去查一个不存在的问题。

### `check-domain.mjs` 的两处误报（已修）

1. **`1.1.1.1` 在这个沙箱里连不上** → dig 吐 `connection timed out` 文本，
   被我的「多解析器 NS 一致性」比对当成「NS 不一致」报警。
   → 改成只比对**真的答了**的解析器，少于 2 个就跳过并说明。
2. **权威 NS 对 `dig +short A blog.nickwu.fun` 只回 CNAME、不回落点 A** ——
   这是**权威服务器应答的正确形态**（它不负责追 CNAME），公共解析器才会替你补 A。
   原来标成 ⚠️ 看着像故障。→ 改成「仅 CNAME（权威应答的正常形态）」。

脚本现在明确知道 apex 留空是**预期**：`nickwu.fun A/AAAA : ✅ 空（预期）`，
并在跑 apex 无记录时提示「别把它当故障修」。
